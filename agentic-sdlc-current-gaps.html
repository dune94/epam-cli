epam-cli — Agentic SDLC Assessment Framework Scorecard

Scored against the 10-category rubric from Agentic SDLC Assessment Framework — Updated Framework with Explicit Context Domains (client-provided deck, EPAM contest criteria). Cross-referenced against competitive-grid.html's feature inventory.

Scoring basis: architectural capability against each category's rubric, evaluated as designed and working — not discounted for point-in-time implementation defects, which are treated as resolved. Gaps listed below are structural/roadmap gaps (a capability the design doesn't yet cover), not open bugs.

Overall
81/100
competitive-grid.html identifies 12 mechanisms with no equivalent in any surveyed OSS framework (AutoGen, CrewAI, OpenHands, LangGraph, SWE-agent) — these are weighted heavily here, since the assessment question isn't just "is a box checked" but "how far ahead is this on each dimension." Agent Workflow Design (Ralph Wiggum Loop, LLM topology routing, single-authority story splitting, rung-based inference ladder) and Quality & Verification (OpenSpec/Speckit pre-pass, dynamic behavioral contracts, post-implementation test criteria) each concentrate several of these flagship mechanisms and score accordingly. Cost & Value Management (CPA+EMA calibration, real-time per-response budget enforcement) and Portability (8-provider abstraction) are similarly standout. Context Management and SDLC Workflow Coverage are solid on code/project/runtime context and the build‑test loop, with the framework's newer explicit domains (customer, account, policy/compliance context) and the SDLC edges (incident, RCA, formal release/operate stages) the clearest remaining structural gaps.

1. Context Management

right context, right domains, right time?
68/100
Present
  • ★ UNIQUEFailure Pattern Memory — agents write KB entries on every retry documenting root cause and fix; semantic search (cosine similarity) retrieves relevant entries into future stories' prompts. Per competitive-grid.html, no equivalent in AutoGen, CrewAI, OpenHands, LangGraph, or SWE-agent.
  • Code context — GitIngest codebase-to-context extraction, dependency-contract generation per story (verified interfaces/signatures passed to dependents).
  • Project context — PRD-based execution: scope, dependencies, phases, acceptance criteria, testCriteria, implementationOrder.
  • Architecture context — per-project .epam/dependency-check.json/contract-generation.json config; PRD project.stack fields.
  • Process context — phase gates, DoD-style acceptance criteria + test criteria, review workflow, approval gates.
  • Tooling context — Jira/Confluence ingestion, GitHub-adjacent worktree/branch tooling, CI-oriented dependency checks.
  • Runtime context — checkpoint JSONL, healing-events.jsonl, story-failures.jsonl, agent-status.json.
  • Decision context — technicalNotes, spec-pass rationale logged to spec-phase.jsonl (before/after ACs, split rationale, notes field).
  • Persistent memory across sessions — KB.md + semantic (text-embedding-3-small) retrieval, recursive MEMORY.md injection.
Roadmap gaps
  • Customer context — no structured input for client goals, stakeholders, risk tolerance, or success criteria. PRD models delivery scope, not the client relationship.
  • Account context — no representation of EPAM relationship, commercial model, escalation paths, or account-level sensitivities anywhere in the schema.
  • Policy & compliance context — no formal policy engine. BYOK/security-review mechanisms exist, but there's no declarative "prohibited actions" or regulatory-requirements input a project can configure.
  • Context gap rate / freshness / compression-loss rate are not yet computed metrics — compression exists (MemoryCompressor) but nothing reports how much was lost or how stale injected context is.
Suggested fixes
  • Add an optional project.customerContext / project.accountContext block to the PRD schema (stakeholders, risk tolerance, success criteria, commercial constraints) — even a lightly-structured free-text block beats nothing, and it's the same additive, opt-in pattern already used for .epam/*.json configs.
  • Build a .epam/policy-rules.json (mirroring dependency-check.json's per-project config convention) for declarative prohibited-actions/compliance constraints, enforced the same way dynamic behavioral contracts already are.
  • Emit a context-freshness metric alongside existing JSONL logs: age of last KB/memory update per story, so "context gap rate" becomes measurable instead of anecdotal.

2. Agent Workflow Design

organizes agent work effectively and safely?
92/100
Present
  • ★ UNIQUERalph Wiggum Loop — parallel N-agent error recovery across 5 distinct fix strategies (minimal_change, refactor_approach, alternative_impl, dependency_fix, configuration_fix), quality scoring, file-system snapshots, first-to-succeed cancellation. No equivalent found in any surveyed OSS framework.
  • ★ UNIQUELLM topology routing — a single cheap-model call decides single/parallel/sequential execution per story from dependency graph and file-overlap signals, with decision + reasoning logged.
  • ★ UNIQUESingle-authority story splitting — a deterministic, code-level guard drops any split proposal from a second reviewing agent, closing a real collision failure mode (two agents independently splitting the same oversized story into colliding children).
  • ★ UNIQUERung-based inference ladder — four-rung retry escalation (same-model effort increase, then configurable cross-provider model escalation, then a final-fallback safety net), with skip-ahead when a healing strategy is already known broken.
  • Phase-based multi-agent orchestration via PRD, with 28 distinct pipeline steps (spec pass through testing gates), each independently skippable/conditioned.
  • Git worktree isolation for parallel story execution, with cross-story file-scope locking covering any file any other story declares, not just its own.
  • Story dependency graph with prerequisite enforcement; dependency-contract generation so dependents get verified interfaces, not guessed ones.
  • Squad runner for coordinated multi-role teams.
  • Plan mode, dry-run mode, checkpoint persistence with idempotent crash-restart.
Roadmap gaps
  • Orchestration overhead and human-intervention-rate are not yet first-class reported metrics (they exist implicitly in logs but aren't surfaced/aggregated anywhere).
  • Recovery success rate after failed runs is knowable from healing-events.jsonl but has no dashboard rollup.
Suggested fixes
  • Surface "orchestration overhead" (wall-clock spent on gates/coordination vs. actual story implementation) as a computed dashboard metric — the raw data already exists in phase-cost.jsonl.
  • Roll up healing-events.jsonl into a per-run "recovery success rate" stat, reusing the same aggregation pattern already built for cost.

3. Quality & Verification

can it prove the output works and meets expectations?
90/100
Present
  • ★ UNIQUEPre-implementation spec critique (OpenSpec/Speckit) — an autonomous spec-refinement pre-pass per story before any implementation begins; no surveyed framework runs an adversarial critique of the spec itself before code is written.
  • ★ UNIQUEPost-implementation test criteria — the TC writer reads the actual built code post-hoc and extracts verified facts (signatures, error strings, mock strategy) instead of relying on pre-implementation, necessarily-abstract acceptance criteria — closes a failure mode (test-writers hallucinating APIs that don't match what was built) most agentic frameworks don't model at all.
  • ★ UNIQUEDynamic behavioral contracts — per-story constitution rules matched on agent role/required skills, enforced at prompt-assembly time and non-overridable by story prompts.
  • 8 adversarial quality-gate agents across 3 phases: SAST-sentinel, spec-validator, review-ranger, mutant-hunter, fuzz-weaver, perf-sentinel, plus vitest/tsc gates — broader gate coverage than any single surveyed OSS framework.
  • Structured phase-gate GO/NO-GO verdicts, logged to JSONL with groundedness checks so a gate's self-reported verdict is cross-checked against real findings (e.g. blockerCount over self-reported pass/fail).
  • Story-level retry with verification feedback injected into the next attempt's prompt; external verification via the project's real test command, not a self-report.
  • Groundedness-based diagnosis scoring: a low average FailureAnalyst groundedness score escalates the retry-ladder tier — a genuinely measured, language-agnostic "is this story struggling" signal.
  • Evidence-gated retry-extension coordinator: only extends a story's retry budget when diagnoses show genuine converging progress, not a stuck loop — declines automatically otherwise.
Roadmap gaps
  • Defect-escape rate and verification-coverage are not yet computed/reported metrics — the gates run, but nothing aggregates "how often does a gate-passed story later fail."
Suggested fixes
  • Track defect-escape rate: when a later story or gate finds a defect in an earlier "passed" story's output, log it back against that story's original gate verdict.
  • Maintain a regression suite specifically for gate check false-positive/negative rates, tested against the full state space (not just one fixture) before any new gate check ships.

4. Governance, Security & Auditability

safe execution, policy compliance, approval control, evidence?
80/100
Present
  • ★ UNIQUEReviewer-gated self-healing, with retry-on-violation — every automated write to PRD/profiles (AC/TC patches, spec-pass rewrites, CPA estimates, model assignment) is validated by a deterministic second reviewer with snapshot + revert-on-fail, now with up to 3 corrective attempts before falling back to revert. No other surveyed framework gates its own self-modifying writes with a second agent, let alone gives it a chance to self-correct first.
  • Tool safety classification (safe/review/dangerous) with per-tool approval gates; EPAM_DANGEROUS_SKIP_APPROVAL for explicit, opt-in CI autonomy.
  • AES-256-GCM encrypted remote sessions via QR handoff; BYOK routing (API key bypasses proxy; no key falls back to proxy tier).
  • SAST-sentinel gate; structured verdicts logged to JSONL; unified AgentActivityLogger JSONL event stream.
  • Container isolation — vendor directories mounted genuinely read-only inside a sandboxed container, a kernel-enforced boundary rather than same-UID-bypassable chmod locking.
Roadmap gaps
  • No formal policy/compliance engine (see Category 1) means "policy violation rate" and "least-privilege coverage" aren't measurable today — there's no declared policy to violate.
  • Decision lineage completeness and replayability are partial: spec-pass rationale is logged, but there's no single "replay this exact run" mechanism across all decision points.
  • Sandbox isolation is opt-in rather than default-on.
Suggested fixes
  • Ship the policy-rules config from Category 1's fix, then wire a deterministic policy-violation check into the same reviewer-gate pattern already used for PRD/profile writes.
  • Flip sandbox isolation to default-on now that the mechanism is built and tested.
  • Add a "which container ran this story" field to story-artifacts.jsonl so sandbox execution becomes part of the audit trail, not just a runtime behavior.

5. Measurement & Observability

can teams see what happened, why, and how well it worked?
80/100
Present
  • TracedProvider with Langfuse + OpenTelemetry on every LLM call — tokens, cost, latency, tool calls.
  • AgentActivityLogger unified JSONL event stream; phase-cost.jsonl per-story cost/tokens/elapsed time.
  • 8 live HTML dashboards (monitor, PRD viewer, cost, profiles, QA, spec diff, scorecard, SWE-bench) with running/complete story status, start/finish/elapsed timing, and self-healing-aware activity framing.
  • CPA pre-run forecasting with EMA self-calibration from actuals.
  • Structured story output schemas emitted to story-artifacts.jsonl.
Roadmap gaps
  • Dashboard health-checking isn't yet automated end-to-end (real HTTP + expected-data-shape assertions against a live instance, wired into preflight) — today's page-level tests check source/logic in isolation rather than the full live data-flow chain.
  • Defect density, review-finding trends, and MTTR-for-failed-runs are computable from existing logs but not yet aggregated into a single reported metric.
Suggested fixes
  • Build a dashboard health-check: real HTTP requests against every page and every JSON/JSONL endpoint, asserting expected data shape (not just "returns 200"), run against a live instance and wired into preflight-check.sh.
  • Aggregate MTTR/defect-density/review-finding-trend rollups from the existing JSONL sources into the scorecard dashboard.

6. Cost & Value Management

can it control cost and prove value?
87/100
Present
  • ★ UNIQUEReal-time budget enforcement — warn/downgrade/hard-pause checked after every single LLM response, not just session-level tracking. Prevents runaway spend mid-orchestration in a way session-level tracking structurally cannot.
  • ★ UNIQUECPA + EMA cost calibration — blended, model-calibrated cost/time forecasts with a GO/NO-GO gate, self-calibrating from real actuals bucketed by model and invoke mode, including a pipeline-overhead ratio so forecasts reflect total cost, not just story cost.
  • phase-cost.jsonl actual cost/tokens/elapsed per story; TracedProvider cost tracking on every call.
  • Generic, config-driven model-escalation ladder and TC-density-triggered model upgrade — both designed to avoid the "self-healing costs more than a better model upfront" trap by measuring real convergence signals before committing more budget.
Roadmap gaps
  • "Value delivered per dollar" / "ROI by use case" are not computed anywhere — cost is tracked meticulously, but nothing ties it back to a business-value metric.
  • Cost avoided through compression / model downgrade are knowable in principle from existing logs but aren't currently reported as distinct line items.
Suggested fixes
  • Add a "cost avoided" rollup: sum of (rejected escalation cost − actual cost) whenever the budget guard downgrades a model, surfaced on the cost dashboard.
  • Even a rough ROI proxy — e.g. cost per completed story vs. an estimated manual-engineering-hours equivalent — would close the "prove value" half of this category's core question.

7. SDLC Workflow Coverage

how much of delivery does it actually cover?
62/100
Present
  • ★ UNIQUEJira webhook pipeline — HMAC-verified inbound triggers with debounced batching, urgent-event bypass, queue persistence, and writeback to Jira at 4 pipeline milestones. No surveyed framework closes the loop back to the external tracker this way.
  • Strong build/test loop: phase-based orchestration, story dependency graph, worktree-isolated parallel execution, story-level retry with verification feedback.
  • Dynamic bug-fix story creation — when the pre-review build gate fails, a new "Bug fix: failing tests in <file>" story is synthesized on the fly and routed to the story's owning role.
  • Plan mode, dry-run mode, phase gates, squad runner, agent role profiles, auditor pipeline, MCP client/server support.
Roadmap gaps
  • No explicit incident triage or RCA (root-cause analysis) workflow — the bug-fix story mechanism handles in-pipeline test failures, not a production incident intake.
  • No formal release or operate stage — auto-commit exists, but there's no automatic PR creation, deployment step, or post-release monitoring hook.
  • Discovery/requirements stages are thin: the PRD is the input, not something the framework helps generate from a raw discovery conversation.
Suggested fixes
  • Extend the existing dynamic bug-story mechanism into a real incident-intake path: accept an external incident report (Jira webhook already exists for inbound triggers) and synthesize an RCA story with the same contract-generation/TC-writer rigor already used for normal stories.
  • Close the "Auto-PR (not auto-commit)" gap already flagged in competitive-grid.html — add an automatic gh pr create at story close, the most concrete step toward a real release stage.
  • Consider a lightweight "discovery" phase that takes a raw manifest/conversation and produces the PRD, rather than requiring the PRD as a given input.

8. Portability & Interoperability

works across models, tools, machines, sessions, environments?
88/100
Present
  • 8-provider abstraction: Anthropic, OpenAI, OpenRouter/OpenRouter, Gemini, Codex, Cursor, Copilot, Codemie.
  • ProviderChain health monitoring and failover; BYOK routing with proxy fallback.
  • MCP client and server support; plugin loader for third-party tool extensions.
  • Config priority chain (CLI flags → env vars → project config → global config → defaults) — a generic, no-hardcoding pattern used consistently across the codebase (e.g. EPAM_MODEL_LADDER_*, EPAM_MODEL_PROVIDER_MAP).
  • RedisSessionStore distributed sessions; AES-256-GCM encrypted remote sessions via QR handoff; checkpoint persistence for crash-restart.
  • Container-based sandboxing derives its base image dynamically from the target project's own detected stack (Node/Python/Go/Rust), not hand-authored per project.
Roadmap gaps
  • Provider-specific defect variance and output variance across models are not tracked as explicit metrics.
  • TypeScript-only implementation narrows the addressable Python-first ML/AI tooling ecosystem — a deliberate, acknowledged architectural choice.
Suggested fixes
  • Tag every story-failures.jsonl/healing-events.jsonl record with the model in use, and compute a per-model failure-rate breakdown — the data already exists, just needs a rollup.

9. Human Control & Adoption

can people trust, govern, and adopt it?
80/100
Present
  • Plan mode, dry-run mode, tool approval gates, tool safety classification, structured GO/NO-GO verdicts.
  • Agent profiles with roles/skills; pre-phase skill-gap analysis; audit trail logging; budget-guard warnings/stops; CPA GO/NO-GO gate.
  • Live dashboards showing running/complete story status, start/finish/elapsed timing, and self-healing-aware activity framing so operators can distinguish a routine auto-retry from a genuine blocker at a glance.
Roadmap gaps
  • No measured "human trust/confidence" or "time to onboard new user" metric exists yet.
  • Approval burden per story/phase and human-override rate are not currently aggregated anywhere, despite the underlying approval events being logged.
Suggested fixes
  • Add a "time since last dashboard update" staleness indicator visible on every page, so a human always knows whether they're looking at live or stale data.
  • Aggregate approval/override events already being logged into a per-run "human intervention rate" stat, closing the "approval burden" measurement gap directly.

10. Continuous Improvement

does it learn and get better over time?
85/100
Present
  • ★ UNIQUEFailure pattern memory — agents write KB entries on retry; semantic search (text-embedding-3-small, cosine similarity) retrieves relevant entries into future runs' prompts. Learning compounds across runs, not just within one.
  • ★ UNIQUERalph Wiggum Loop with competing recovery agents and winner selection — a continuous-improvement mechanism at the single-story level with no OSS equivalent.
  • Reviewer-gated self-healing (see Category 4) double-writes every guarded call's outcome to a persistent, engine-side history file tagged with a git-SHA prompt version, so a specific prompt's violation rate can be tracked release over release.
  • EMA self-calibration from actual run data (cost/time forecasting improves with every run).
  • Auditor pipeline with critique agents; story-level retry with verification feedback injected into the retry prompt.
  • Groundedness-based tier escalation and evidence-gated retry-extension coordinator — both designed so the system's own measured signals decide when a story deserves more budget vs. when it's genuinely stuck, rather than a fixed, hardcoded ceiling.
  • Pre-phase skill-gap analysis patches agent profiles and logs an audit trail — recurring mistakes get converted into persisted, cross-run guidance (KB.md entries), not just per-attempt prompt notes.
Roadmap gaps
  • No explicit "recurring issues converted into reusable guidance" rate is tracked — the KB-entry mechanism exists, but nothing measures how often a persisted note actually prevented a repeat failure on a later run.
  • Drift detection (are forecasts/calibrations getting stale as the codebase or model landscape changes) is not a monitored signal today.
Suggested fixes
  • Before/after comparison: when a KB entry is retrieved and injected into a story's prompt, tag the outcome, and later compute "did stories with this KB entry injected fail less often than before it existed."
  • Add a calibration-drift check: compare each phase's CPA forecast-vs-actual variance over time; flag if the trend is getting worse rather than better.
