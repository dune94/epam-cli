epam-cli — Install & Run Guide

Deploying the orchestration pipeline without the TypeScript source. Five flows, each complete on its own.

Read this first. This guide describes a deployment that has not been built yet. It is grounded in the real scripts, paths and variable names in the repository, and every step marked verified was read out of the code. Steps marked unverified are reasoned but not executed — the installer (install.sh) and the release builder do not yet do everything described here. Treat this as the target, not a record of something that already works.

1. The .env file — do this first

Every credential lives in one file, written by hand. The installer never prompts for a secret, never writes one, and never creates per-project credential files. It copies .env.example to .env and asks you to fill it in.

On the claude and codemie stacks you need exactly two values. Neither stack requires an LLM API key: claude authenticates through its own OAuth session on disk, and codemie-claude through CodeMie SSO. This is declared in orchestrations/config/provider-sets.json, where both sets have "credentials": []. verified

A complete, working .env for the claude stack:

JIRA_EMAIL=you@yourcompany.com
JIRA_TOKEN=your-atlassian-api-token

What each key is for

KeyclaudecodemieWhy
JIRA_EMAILrequiredrequiredingest-jira-tickets.sh:81-85 exits 1 without it
JIRA_TOKENrequiredrequiredsame check; also the project's REQUIRED_KEYS
ANTHROPIC_API_KEYdo not setSee the warning below
OPENROUTER_API_KEYnot needednot neededOnly the openrouter stack declares it
MINIMAX_API_KEYnot needednot neededOnly the openrouter stack declares it
LANGFUSE_SECRET_KEY
LANGFUSE_PUBLIC_KEY		optionaloptionalTracing. Disables itself cleanly when unset
Do not put ANTHROPIC_API_KEY in .env. Claude Code prefers an API key over the OAuth session on disk, so setting it bills an API account while the subscription you pay for goes unused. This is not hypothetical: llm-defaults.claude.json records seven runs billed to the wrong account before anyone noticed, and it surfaced only when the credits ran out mid-run. The runner now scrubs the variable, but the safe state is not writing it at all. verified
Where the file lives depends on the layout you install into. In the versioned layout it is /opt/epam-cli/state/.env; in a flat install it sits at the install root. It is loaded first by orchestrate.sh:107 either way.

2. Flow A — Windows + Docker (via WSL2)

The pipeline runs inside WSL2. PowerShell is only a front door. This is not a preference — the engine is ~52,000 lines of bash using flock, setsid, POSIX process groups and /proc, none of which have native Windows equivalents. verified

Prerequisites

  • Windows 10 build 19041+ or Windows 11
  • Administrator rights (for the one-time WSL2 install)
  • Docker Desktop, with the WSL2 backend enabled
  • The release .zip

Steps

1Extract the .zip. Right-click → Extract All.A folder containing install.ps1 and a .tar.gz
2Open PowerShell as Administrator and run:
wsl --install -d Ubuntu
Ubuntu installs. A reboot is usually required. Reboot before continuing
3After reboot, launch Ubuntu once from the Start menuYou are asked to create a UNIX username and password. Do so
4In Docker Desktop: Settings → Resources → WSL Integration, enable your Ubuntu distro, Apply & RestartIn Ubuntu, docker info succeeds
5In the extracted folder, right-click install.ps1 → Run with PowerShellIt reports what it will do before doing it unverified
6(installer) copies the tarball into the distro and expands it inside LinuxSymlinks and file modes survive. Expanding on the Windows side would break them
7(installer) installs prerequisites inside Ubuntu:
sudo apt-get update
sudo apt-get install -y git jq python3 python3-pip shellcheck
All five resolve. shellcheck is the one people forget and it is a hard requirement
8(installer) installs the runner — claude or codemie-claudeclaude --version prints a version inside Ubuntu

Verify it actually works

Not "files exist" — make it do something:

# 1. The SDK bundle loads. This is the exact call the engine makes.
node -e "console.log(Object.keys(require('/opt/epam-cli/current/dist/sdk.js').FIXED_AGENT_ROLES).length)"
# → a non-zero number

# 2. The executor can see the projects
/opt/epam-cli/current/orchestrations/scripts/pipeline --list
# → a table of PROJECT / PREFIX / CODELINE

# 3. Full validation, spends nothing
/opt/epam-cli/current/orchestrations/scripts/pipeline --jira AMSD-1234 --dry-run
# → "✓ ready", then ticket/project/stack/docker lines, then "--dry-run: nothing started"
Checking that dist/epam.js exists is not a valid verification. In the current repository that file is a 188-byte stub that prints Hello, World!. Always execute something. verified

3. Flow B — Windows without Docker (via WSL2)

Docker is genuinely optional. No container takes part in producing a result — every one is somewhere the pipeline reports to. The dashboards are rendered by a normal process on the host and written to disk as static HTML; Docker only serves them over HTTP. Without Docker you lose the web view, not the data. verified

Steps

Identical to Flow A, with these differences:

  • Skip steps 4 and 11 entirely. Docker Desktop is not needed.
  • At step 5, run the installer in explicit no-docker mode so the choice is recorded rather than inferred: 
    .\install.ps1 -NoDocker
    unverified — the PowerShell wrapper does not exist yet

What you will see, and should not try to fix

The executor prints this line, and it is correct and expected:

docker    dashboards unavailable (docker not running) — the run itself does not need them

That text comes from orchestrations/scripts/pipeline:124. It is informational. The run proceeds. verified

One real caveat. Most of the older launchers (the tier3-*-run.sh family) run a pre-flight that hard-fails when the dashboard, Langfuse and Grafana are not answering — it will exit 1 before starting. The pipeline executor avoids this because it hands off to orchestrate.sh, which does not run that pre-flight. On a no-Docker install, use pipeline and do not call the tier3-* scripts directly. verified

You will be asked to confirm spending before anything starts. If the project enables the human review points (EPAM_PAUSE_AFTER_AGENT_MINT, EPAM_PAUSE_BEFORE_WRITER), the run will also stop twice and wait for you — once after the agent roster is built, once before any code is written. That is intended behaviour, not a hang. verified

Steps

  • Skip step 10.
  • At step 8, be explicit: 
    cd /opt/epam-cli/releases/1.6.0

Verify

node -e "console.log(Object.keys(require('/opt/epam-cli/current/dist/sdk.js').FIXED_AGENT_ROLES).length)"
/opt/epam-cli/current/orchestrations/scripts/pipeline --jira AMSD-1234 --dry-run

Expect ✓ ready and the dashboards unavailable note. Both are correct.

Getting at the dashboards without Docker

The pipeline still renders dashboard HTML to disk during a run, at orchestrations/dashboards/live/. You can open those files directly in a browser. To turn the renderer off entirely:

export EPAM_DASH_AUTO_SERVE=0
On first use the renderer may try to fetch its own dependency with npx, which needs network access. If the machine is offline and you do not want dashboards, set EPAM_DASH_AUTO_SERVE=0. verified

6. Flow E — Driving a run over HTTP / Postman

Today you cannot start a run from Postman. The HTTP API that exists is a run-control API, not a run-invocation API. None of its six routes launches a pipeline. The Jira webhook route queues an event and eventually writes a webhook-prd-*.json file that nothing reads — the queue module imports only fs and path, with no process-spawning code anywhere in it. verified

This section has two halves. 6.1 is what works today. 6.2 is the launch capability that has been designed but not built — read it as a specification, not as instructions.

6.1 What works today — steering a run in flight

Prerequisites

  • A run must already be in progress. The server is started by the orchestrator and stops when the run stops.
  • You need the port (see below) and, for signed webhooks, JIRA_WEBHOOK_SECRET.

Finding the port

SituationPort
CONTROL_PLANE_PORT set explicitlyThat value — an override always wins
Single-codeline run8094
Jira / brownfield run (the normal case)8095, 8096, 8097… — one per codeline. 8094 is not used
On a Jira run the parent orchestrator exits before it would start a control plane, so nothing ever binds 8094. Each parallel codeline lane runs its own server at 8094 + 1 + <lane index>. There is no aggregate endpoint across lanes — you talk to one lane at a time. verified

Confirm what is actually listening:

ss -ltnp | grep -E '809[4-9]'
# or
curl -sf http://localhost:8095/health && echo " ← alive"

The endpoints

MethodPathWhat it does
GET/health200, empty body
GET/status{ paused, pendingRedirects[] }
POST/pauseRun blocks at the next story boundary
POST/resumeRun continues
POST/redirect/:storyIdReassign a story to a different agent
POST/webhook/jiraQueues an event. Starts nothing.

Postman-ready examples

GET http://localhost:8095/status
→ 200
  { "paused": false, "pendingRedirects": [] }


POST http://localhost:8095/pause
  Content-Type: application/json
  (no body needed)
→ 200
  { "paused": true }


POST http://localhost:8095/resume
→ 200
  { "paused": false }


POST http://localhost:8095/redirect/AI-1234
  Content-Type: application/json

  { "targetAgent": "backend-implementation-agent" }

→ 200
  { "storyId": "AI-1234",
    "targetAgent": "backend-implementation-agent",
    "requestedAt": "2026-09-02T10:00:00.000Z" }
→ 400 if "targetAgent" is missing or blank


POST http://localhost:8095/webhook/jira
  Content-Type: application/json
  X-Hub-Signature-256: sha256=<hmac>      (only checked if JIRA_WEBHOOK_SECRET is set)

  { "webhookEvent": "jira:issue_created",
    "issue": { "key": "AMSD-1234", "fields": { "summary": "..." } } }

→ 202  { "status": "queued", "jiraKey": "AMSD-1234", "urgent": false }
→ 202  { "status": "ignored", "reason": "unrecognised event type" }

Response shapes were read from the source, not round-trip tested — exercising /pause means interfering with a live paid run. unverified at runtime

Calling it from Windows against a WSL2 run

The server binds 0.0.0.0 deliberately, and a test asserts this is for WSL2 reachability. http://localhost:8095 from Windows usually works via WSL2's localhost forwarding. If it does not, get the distro's address:

wsl hostname -I     # → e.g. 172.24.83.191
# then use http://172.24.83.191:8095

unverified — the forwarding path was not tested

6.2 Launching a run over HTTP — DESIGNED, NOT BUILT

None of this section works yet. There is no launch service in the repository. The endpoint, the payload and the responses below are a design, recorded so the intent is reviewable before anyone writes code. Do not try these calls — nothing is listening. not implemented

Why it needs a new service

The control plane in 6.1 is started by the orchestrator and dies with it. Something started by the orchestrator cannot start the orchestrator — when no run is going there is nothing listening. Launching therefore needs a second, small, always-on service whose lifetime is the machine's rather than a run's. The two do not overlap:

Launch service (new)Control plane (exists)
Lifetimealways onone run
Started bythe OS, as your userthe orchestrator
Portone, fixed8095+, one per codeline
Can start a runyesno
Can steer a runnoyes

The planned endpoint

POST http://127.0.0.1:8099/launch
  Authorization: Bearer <EPAM_LAUNCH_TOKEN>
  Content-Type: application/json

  { "ticket": "AMSD-2041" }

→ 202 Accepted
  { "status": "launching",
    "ticket": "AMSD-2041",
    "resolvedJql": "issue = AMSD-2041",
    "project": "metrolinx",
    "providerSet": "claude",
    "runId": "20260902T101500Z",
    "pidFile": "/tmp/tier3-metrolinx-run.pid",
    "logFile": "/tmp/tier3-metrolinx-20260902T101500.log",
    "controlPlanePortBase": 8095 }

→ 409  a run is already in flight for that project
→ 401  missing or wrong token
→ 422  no project declares that ticket prefix
→ 400  the ticket id is malformed
→ 503  pre-launch validation refused (problems listed)
Why 202 launching and never 200 started. The launchers detach into their own session with setsid. Measured against that exact pattern: the caller gets exit code 0 after 0 seconds, before the run has written even its first log line. The exit code says "the fork happened" and nothing more. So the service reports launching, then confirms real liveness from the pid file. It can never report "finished" — it is not the run's parent and cannot see its exit status. measured

Planned read-only routes

GET /health
GET /projects                       # the ticket-prefix table
GET /runs                           # every live /tmp/tier3-*.pid
GET /runs/metrolinx                 # { running, pid, runId, logFile, controlPlanePorts[] }
GET /runs/metrolinx/log?tail=200    # tail the run's log

To follow a run after launching it, poll GET /runs/<project>, then use the 6.1 routes on controlPlanePorts to pause, resume or redirect it.

Auth — deliberately minimal

One shared secret, one line in your .env, exactly like every other credential:

EPAM_LAUNCH_TOKEN=generate with: openssl rand -hex 32
  • Checked on every route as Authorization: Bearer <token>.
  • The service refuses to start if the variable is missing — it does not warn and carry on.
  • Binds 127.0.0.1 by default. Exposing it to the Windows host is an explicit opt-in.
Why the token is not optional. The pipeline normally asks you to confirm spending before it starts, and only an explicit opt-in skips that prompt. A launch API has no terminal, so the API call becomes your "yes". An unauthenticated launch endpoint is therefore an unauthenticated way to spend money on your LLM account. The existing control plane's "accept everything when no secret is set" default must not be copied here.

What it will deliberately refuse to do

  • Run any command you supply. The only input reaching a process is a ticket id, validated against ^[A-Z][A-Z0-9]+-[0-9]+$ first, passed as an argument and never through a shell.
  • Skip pre-flight, or set any of the pre-flight bypass variables.
  • Skip the human review pauses.
  • Run as root.
  • Start a second run for a project that already has one — it returns 409, using the same /tmp/tier3-*.pid file the kill script already relies on.
The one defect that must be fixed before this is safe. Today the executor accepts a ticket id and then ignores it: the ticket actually run comes from the project's configured JIRA_JQL. Over HTTP that is far worse than at a terminal, because the response would confirm the ticket you asked for while a different one ran — a machine-generated, authoritative answer that is wrong, costing real money. That plumbing must be fixed first, and the 202 body deliberately echoes resolvedJql so the mismatch cannot hide. verified defect

Rough effort for the whole capability: about five to six working days, of which the ticket-plumbing fix is a mandatory half-day that must come first.

6.3 Security of the API that exists today

Security: there is no authentication by default. Five of the six routes never check a signature. The sixth checks one only if JIRA_WEBHOOK_SECRET is set, and if it is unset the code explicitly accepts everything (// dev mode — accept all). The socket is bound to all interfaces. /pause and /redirect change the behaviour of a paid run in flight. On a laptop this is usually fine; on a shared or client network, do not expose these ports. verified

7. Troubleshooting

These are failure modes found in the code, not generic advice.

SymptomCause & fix
jq is not installedThe engine parses JSON with jq in roughly 700 places. sudo apt-get install -y jq
Pre-flight fails mentioning shellcheckA hard pre-flight dependency that runtime checks miss. sudo apt-get install -y shellcheck
the '<stack>' stack runs 'claude', which is not on PATHThe runner is missing, or installed for a different user/shell. Check with command -v claude inside WSL, not in PowerShell
Runner found, but every call fails--version proves the binary, not the session. Sign in: run claude once interactively, or re-authenticate CodeMie SSO
Run starts, then dies with a credit or billing errorANTHROPIC_API_KEY is set somewhere and outranks your OAuth session. Remove it from .env and your shell profile
A tier3-* script exits immediately, complaining about Langfuse, Grafana or the dashboardThat pre-flight requires Docker services. On a no-Docker install use pipeline instead
MINIMAX_API_KEY is not set on a claude installYou are running tier3-metrolinx-run.sh, which demands two vendor keys unconditionally regardless of stack. Use pipeline — it asks the active stack what it actually needs, and the claude stack needs none
no project declares the ticket prefix 'XXX'Each project declares JIRA_PROJECT_KEY in its config.env. Run pipeline --list to see the mapping
Jira ingest returns nothingCheck JIRA_URL, JIRA_EMAIL, JIRA_TOKEN. Also check the project's JIRA_JQL — if it is pinned to a specific issue, that is what runs
docker compose up -d appears to do nothingThere is no root docker-compose.yml. Pass -f docker-compose.observability.yml
Port 3001 conflictdocker-compose.epam-cli.yml and docker-compose.observability.yml both claim it. Start one, never both
wsl --install seems to do nothingIt usually needs a reboot. Reboot, launch Ubuntu once from the Start menu to create your UNIX user, then continue
Windows cannot reach localhost:8095Use wsl hostname -I and address the distro IP directly
Dashboards never appear during a runThe renderer may need npx and network access on first use. Set EPAM_DASH_AUTO_SERVE=0 if you do not want them
The run stops and appears to hang, twiceThose are the human review points. Resume with EPAM_RESUME_RUN=<run-id>
Install "succeeded" but nothing runsDo not trust file-existence checks. Run the three verification commands in your flow — especially the FIXED_AGENT_ROLES one
