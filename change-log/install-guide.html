epam-cli — Install & Run Guide

The real, current install path — verified against the actual installer scripts, 2026-09-04.

1. Install — npx amsd-pipeline

No git commands required. This clones the repo itself, packages the requested ref into a fresh tree at --dest, then runs every step below against that tree.

npx amsd-pipeline --dest ~/amsd-pipeline

From an existing checkout, the same script works directly, in place:

./orchestrations-installer/install.sh                    # install for the default stack, with dashboards if docker is up
./orchestrations-installer/install.sh --stack codemie     # install for a specific stack
./orchestrations-installer/install.sh --no-docker         # skip dashboards entirely
./orchestrations-installer/install.sh --check             # verify an existing install, change nothing
./orchestrations-installer/install.sh --dest ~/somewhere --ref v1.7   # package that ref into a NEW tree, then install it

Re-running install.sh against an existing --dest is an UPDATE, not a fresh install: app code updates, but an operator's edited project config (config.env, llm-settings.json, five engine-wide orchestrations/config/*.json files) and accumulated run state (orchestrations/logs, phase-cost.jsonl, KB files) both survive untouched.

Prerequisites install.sh checks for: git, jq, node, python3 (88 pipeline handlers are pure-stdlib python3), and the declared stack's own runner (claude, or an internal EPAM tool codemie-claude obtained through your organization's own distribution — this repo does not install either CLI itself).

2. Docker or Podman — no Docker Desktop license needed

install.sh discovers whichever is on PATH — Docker first, Podman as a fallback (EPAM_CONTAINER_RUNTIME to force one). Docker Desktop requires a paid subscription above 250 employees or $10M revenue — that is a procurement conversation, not a technical requirement, and this installer never needs it: install Docker Engine directly inside a WSL2 Ubuntu distro (the standard apt-based Docker CE install), or use Podman, either is fully supported and tested (test/unit/orchestration/the-installer-installs-on-podman.test.ts). Neither docker nor podman is required at all — pass --no-docker and the pipeline itself still runs; only dashboards and the launch UI are unavailable.

Every docker resource — container names, network subnet, ports — is isolated per install, deterministically, so two installs (or an install alongside a hand-run dev checkout) never collide on the same machine.

3. The .env files

Several separate files, each scoped to a different concern — documented here in full because an earlier version of this install flow omitted some of them entirely and it caused real confusion mid-run:

FileHolds
Root .envProvider credentials (OPENROUTER_API_KEY, MINIMAX_API_KEY — only for the openrouter stack) plus feature-scoped vars (JIRA_EMAIL/JIRA_TOKEN, LANGFUSE_SECRET_KEY/LANGFUSE_PUBLIC_KEY, GITHUB_PERSONAL_ACCESS_TOKEN). Generated by install.sh from provider-sets.json + env-vars.json — a var added to either needs no installer edit. The claude stack needs none of these: it authenticates via claude login (an OAuth session on disk), and an ANTHROPIC_API_KEY present here outranks that session and silently bills the API account instead — leave it unset for the claude stack.
launch-dashboard/.envLAUNCH_PASSWORD (a fixed default, abcd1234, the same on every fresh install — change it via the dashboard's own change-password flow after your first login) and LAUNCH_UI_PORT.
A project's own config.envOperational settings, not secrets — JIRA_URL, JIRA_PROJECT_KEY, JIRA_CODELINE_ROOT (the brownfield discovery root — a real host path to the client repos), etc. Preserved across installer updates.
A project's own orchestrations/jira/<project>.envPer-project Jira credentials, when a project's config.env declares SECRETS_FILE= pointing at it — an opt-in override of the root .env defaults, for running against multiple clients' Jira instances without sharing credentials. Not provisioned by install.sh at all — supply it yourself per project, or Jira ingestion fails at launch.

4. The launch dashboard & runner

install.sh provisions the launch dashboard (Flutter frontend + Node backend) fully by itself: builds and isolates its docker stack, creates launch-dashboard/.env with the default password, and starts runner-host.js — the HOST process (not dockerized; a container cannot exec a host process) that actually polls the spool and launches real pipeline runs — as a managed, pidfile-tracked daemon. A second daemon, snapshot-watch.js, is also started automatically: it keeps agent-monitor's build-info.json fresh, and without it every launched run's own pre-flight hard-fails immediately.

5. Bouncing services — pipeline-services.sh

For a WSL restart, or just wanting to restart cleanly, without losing any data (never -v, never --rmi — this is a pause, not an uninstall):

bash orchestrations-installer/pipeline-services.sh --stop
bash orchestrations-installer/pipeline-services.sh --start

--start reconnects to the exact subnet/ports/project identity the original install resolved (persisted in .pipeline-services-state.env), never re-rolling a different one.

6. Checking readiness — pipeline-health.sh

A different question from install.sh --check ("did the install complete") — this asks "can I launch a real run from here, right now":

bash orchestrations-installer/pipeline-health.sh

Checks platform/tooling, probes the container runtime rather than trusting command -v, reads the active provider set live and flags the API-key-outranks-OAuth trap explicitly, checks memory/disk headroom, verifies a selected project's codeline-discovery root actually resolves to git repos, and confirms both host daemons (runner-host.js, snapshot-watch.js) are actually running — reporting unhealthy, not just a warning, if either is declared but not running.

7. Uninstalling

bash orchestrations-installer/install.sh --uninstall --dest ~/amsd-pipeline

Removes this install's docker footprint — containers, network, volumes, locally-built images — and stops both host daemons. Structurally incapable of touching another install or the dev checkout: an isolated install's project names never share the dev checkout's own naming shape, by construction. Files on disk are never touched; remove the directory yourself once you are done with it.

8. Troubleshooting

SymptomWhat it means
Install reports "ready" but the dashboard login failsThe running container may have started before a .env edit — the file and the live process can desync. Restart with pipeline-services.sh --stop then --start to pick up the current file.
A launched run fails pre-flight instantlyRun pipeline-health.sh first — it checks exactly the things a run's own pre-flight also checks (both host daemons, credentials, memory), before you spend anything.
"MINIMAX_API_KEY is not set" on the claude stackA known gap in some project launcher scripts that check for every vendor's key unconditionally, regardless of the active stack — not something install.sh itself requires for claude.
A saved run stays "pending" forever after it actually failedThe dashboard's database and the pipeline's own status file can desync — check launch-dashboard/spool/status/<id>.json for the real outcome.
