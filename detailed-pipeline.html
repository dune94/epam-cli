1. Setup (one-time, per project)

Covered at a conceptual level in onboarding.html. Technical entry points:

epam new init & epam new generate

src/cli/commands/new.ts — two subcommands:

  • epam new init <path> → runInit() → instantiates ProjectScaffolder (src/scaffold/ProjectScaffolder.ts) with an empty PRD skeleton; writes directory structure, no LLM call.
  • epam new generate <path> → runGenerate() → reads manifest.md, calls three LLM phases in src/scaffold/ManifestAnalyzer.ts:
    • analyzeManifest() → { summary, projectName, suggestedPrefix, techStack, questions } — may surface clarifying questions to the human before proceeding.
    • proposeAgents() → project-specific profiles.json entries (name, systemPrompt, rationale), given the manifest plus the clarification Q&A. This is the FIRST agent-generation event in a project's life — see §4.
    • generatePrd() → the actual prd.json (stories + implementationOrder)
src/cli/commands/new.tssrc/scaffold/ManifestAnalyzer.tssrc/scaffold/ProjectScaffolder.ts
Manifest-driven config generation (.epam/*.json)

Scaffolding also produces the stack-specific manifests the engine reads at runtime — the engine itself contains zero language/stack assumptions; everything stack-specific lives in these files:

  • .epam/dependency-check.json — manifest file name, import-detection regex, install command, ignore-list, required dev dependencies, and vendorDirs (vendor-directory tamper-protection targets, e.g. node_modules)
  • .epam/contract-generation.json — regex/templates used to auto-generate .contracts/<storyId>.md dependency contracts from real source
Entry points to actually launch a run
  • epam orchestrate --phase <id> --prd <path> --output-dir <path> (src/cli/commands/orchestrate.ts) — generic wrapper; spawns run-agent-orchestration.sh as a child process, forwards PRD_FILE/OUTPUT_DIR/EPAM_ORCHESTRATION_PROVIDER as env vars.
  • Direct: bash orchestrations/scripts/run-agent-orchestration.sh --phase <id> — reads PRD_FILE/OUTPUT_DIR from env, not CLI flags.
  • Project-specific launcher scripts (e.g. tier3-travel-app-run.sh) wrap the above with project-specific env (model assignments, teardown/rebuild of the output directory, gate-model configuration) and run all configured phases in sequence.
  • recent Project-specific launchers now re-exec themselves under setsid and write their own PID to a pidfile (TIER3_PID_FILE), so the whole descendant process tree can be killed with one command instead of hunting orphaned children individually — see orchestrations/scripts/kill-tier3-run.sh.

2. Phase Execution Pipeline

Everything below runs once per phase, in this order, driven by run_testing_gates() and the surrounding step sequence in orchestrations/scripts/run-agent-orchestration.sh. Self-healing and guard mechanisms are described at the step where they actually fire, not in a separate section — several of them (scope guard, vendor guard, the inference ladder) recur at multiple steps, and are cross- referenced rather than repeated in full.

Step 0 — Specification pass fixed

Elaborates and validates the phase's stories before any implementation begins. Two sub-agents run per story:

  • 0a — openspec (openspec-agent): elaboration. Given a story's id/title/description/ACs/technicalNotes/dependencies/agentRole, produces refined acceptance criteria in strict JSON, may propose splits, preserves existing detail unless improvement is required, and enforces the ROLE ASSIGNMENT RULE — any child story whose files are only *.test.ts/*.spec.ts must get agentRole: test-engineer, never the same role as its paired implementation story.
  • 0b — speckit (speckit-agent): verification, operating like the hosted Speckit workflow — converts requirements into executable specs, highlights missing ACs, and recommends decompositions. Designed to complement openspec's output, not duplicate it (system-level coverage, interface contracts, verification steps) and applies the same role-assignment rule independently.

Before openspec/speckit run, three pre-spec sub-stage agents may groom the backlog: readiness-checker validates stories against INVEST criteria and a configurable checklist; grooming-coordinator orchestrates that backlog-grooming pipeline; dedup-detector flags semantically overlapping or conflicting stories before they're elaborated. spec-coordinator-agent reads the PRD before every phase, evaluates risk/dependencies/technical readiness, and decides which spec personas actually need to run.

Every proposed change (AC edits, splits, profile edits) from any of these agents passes through run_prd_change_reviewer() before being accepted — see §2, Step 4.2 sequencing below and §3.

Split governance rules (all deterministic, code-level checks — not left to LLM judgment):

  • Split coherence: rejects a split where multiple children would write to the same file (silent last-writer-wins data loss).
  • AC cap enforcement: caps any single story at 24 acceptance criteria; forces a split above that.
  • Split mandate: if a story exceeds the cap and wasn't split, forces one retry; if the retry still doesn't resolve it (e.g. a lazy split that just copies the full AC list to one child), the violation is flagged for the next specification pass rather than retried indefinitely.
Step 0.1 — CPA pre-pass (Cost/Complexity Assessment) fixed

Runs contextualize-stories.sh, which per pending story builds a rich context payload and pipes it to lib/cpa-inference.js for LLM review:

  • Formula estimate — a deterministic baseline (aiMinutes, cost, tokens, turns) computed from the story's effort/type before any LLM involvement.
  • Codebase signals — total LOC, file count, import count, whether referenced files already exist, plus relevant file snippets.
  • KB retrieval — semantically-matched knowledge-base chunks for the story's required skills (empty section noted explicitly if none match).
  • Adjacent stories — sibling story id/title/effort/status for context.
  • Prior-phase handoff — the most recent phase-handoff-<phase>.md from another phase (if any) is injected so the estimate accounts for what already landed.

The LLM returns a structured review: confidence, complexityAdjustment, adjustedEstimate (the blended final numbers), riskFlags, missingKbCoverage, citedSources, and reasoning. If the inference call itself is unavailable, a skippedReview() fallback returns the formula estimate unchanged with confidence: 0.70 rather than blocking the phase.

Gate outcome, by contextualize-stories.sh's exit code:

  • 0 — pass: all stories cleared, phase proceeds normally.
  • 2 — review: one or more stories carry elevated risk; the phase continues with a warning unless STRICT_CPA=1 is set, in which case this halts the phase for human review.
  • 3 — block: one or more stories cannot proceed at all; the phase halts (exit 3) regardless of STRICT_CPA. Override: SKIP_CPA=1 to bypass the gate entirely.

Every write this step makes to a story's estimate fields (estimatedAiMinutes/estimatedCost/estimatedTokens/estimatedTurns/effort/cpaConfidence/cpaGate) is validated by prd-change-reviewer before being accepted, with surgical per-field revert (not whole-file) on rejection — see §3.

Step 0.5 — Pre-phase skill assessment fixed

Run by team-lead-agent in PRE-PHASE mode (or a phase-scoped assessment agent, depending on wiring) before the phase's stories execute. This step is where agent generation happens mid-project, not just at initial scaffolding — see §4 for the full mechanism:

  • Verifies every story's agentRole matches what its declared files actually require (e.g. a test-only story must have agentRole: test-engineer, never shared with its paired implementation story).
  • Profile creation: if a story needs a role that doesn't exist yet in profiles.json, this step can create the profile from scratch, based on the project's techStack.
  • Skill-gap fill: for each story, compares the assigned role's existing profile text against the story's technicalNotes.requiredSkills and appends missing-skill sentences as needed — proactive, before the story ever fails, not reactive self-heal.

Step 0.7 — Regression guard fixed

Bypass: SKIP_REGRESSION_GUARD=true. Guards against reintroducing a previously-fixed failure pattern in the same phase.

Step 0.8 — mkdir src/ dirs fixed

Ensures the directory structure declared in stories' technicalNotes.files exists before implementation begins.

Step 0.9 — PRD model coordinator fixed

Run by prd-model-coordinator, once per phase after the specification pass has elaborated stories and created any split children, before story execution begins. Fills in model/ aiProvider/reasoningEffort for any pending story missing one or more of these fields — never overwrites a pre-existing value, and split children inherit their parent's assignment when the parent has one, rather than silently falling back to a provider's hardcoded default. Runs with tool access (writes the PRD back to disk); its own writes go through prd-change-reviewer, which additionally rejects any change touching a field other than model/aiProvider/ reasoningEffort on any story.

Step 1 — Main-branch stories (the implementation loop) fixed

The core loop: each main-branch story is implemented in sequence by its assigned agent role (a project-specific implementation role — see §3). Each attempt goes through:

  • Scope guard (_scope_lock/_scope_unlock, claude.sh:1327) — makes files outside the story's own declared scope, and files owned by other stories, read-only for the duration of the attempt. Restores out-of-scope files from a pre-run snapshot before external verification, so Bash-written files bypassing tool-level guards can't contaminate another story's test results.
  • Vendor guard (_vendor_lock/_vendor_unlock/run_vendor_integrity_check, claude.sh:1420+) — makes configured vendorDirs (e.g. node_modules) read-only during the attempt, and separately verifies (via mtime) that they weren't tampered with even if the lock itself were bypassed. Config-driven — the engine has zero hardcoded vendor-directory names.
  • Plan-then-execute (high-complexity stories only) — check_plan_mode_required() (claude.sh:637) triggers a planning turn when estimatedHours ≥ 6, dependency count ≥ 2, or an explicit planModeRequired flag is set. run_plan_mode/run_planning_phase produce a numbered execution plan from the story's ACs; review_and_correct_plan checks it against real dependency contracts (ground-truth exports from already-completed dependency stories) and requests one corrective re-plan if it contradicts them. recent run_plan_mode's prompt explicitly says "Read orchestrations/prd.json for story X" and now runs with tool access to actually do that — previously it had none, so the plan was fabricated from whatever the model guessed rather than the real PRD content.
  • Implementation call — the agent writes code against the story's acceptance criteria / test criteria (TC — see §3, Step 1.6 below).
  • Dependency contracts — if the story declares dependencies, auto-generated .contracts/<depId>.md files (real exported class/function signatures, not model-transcribed) are available as ground truth to the plan reviewer and, on failure, the failure analyst.
  • External verification (run_external_verification, claude.sh:2216, and run_tsc_verification, claude.sh:2418) — runs the project's real test command and a real tsc compile check outside the agent's own turn, so a story can't self-report success. A tsc failure sets the same VERIFICATION_FAILURE channel as a test failure, so it gets full retry-ladder treatment instead of exiting the phase on the very first compile error.
  • On failure — retry & escalation: assess_model_escalation (claude.sh:2949) classifies the failure as env / capability / quality / unknown and decides whether to escalate the model and/or inject a targeted prompt amendment. The retry loop runs four rungs (two attempts each, EPAM_MAX_RETRIES default 7 → 8 total attempts): Rung 0/1 keep the base model and raise reasoning effort low→medium; Rung 2 escalates the model via a tier-aware ladder (EPAM_MODEL_LADDER_MEDIUM/_HIGH — see §5); Rung 3 keeps the escalated model at high effort. check_healing_effectiveness/check_failure_diversity (claude.sh:4034/4139) detect the SAME failure signature recurring 2-3+ times despite self-heal attempts ("HealingBroken") and force a rung-skip rather than retrying at the same tier indefinitely.
  • Deep diagnosis — run_failure_analyst (claude.sh:3322) diagnoses the root cause and prescribes a fix, routed to one of prd (AC patch) / tc (test-criteria patch) / skill (profile addendum) / kb (knowledge-base entry) / tool (synthesize a dynamic shell helper — see §4) / none. All context (test failure output, TC facts, skill addendum, dependency contracts) is injected as text — the analyst never needs file access itself. recent Dependency-contract injection was added after a live diagnosis error: the analyst called a casing-typo'd import a "default vs named export mismatch," which was false — the class was correctly a named export, just mis-cased — and every retry (including the strongest configured model) then "fixed" the wrong thing because the diagnosis guiding it was wrong.
  • Deterministic pre-checks run before any of the above, wherever the failure mode is mechanically checkable — see §4. If one of these fires, it can grant a "free retry" not counted against the escalation ladder.
Step 1.5 — Auto-commit fixed (conditional)

Only runs if there are uncommitted main-branch changes after Step 1. Every completed story is auto-committed as part of its own completion ("story: complete <id> (N file(s))") — this step catches anything left over.

Step 1.6 — TC writer gate fixed (conditional)

Run by tc-writer-agent — bridges the gap between spec-authored ACs (written before the code exists, necessarily abstract) and implementation reality. Reads the paired implementation story's real source after it completes and extracts verified facts (sourceFiles, facts, mockStrategy, bannedPatterns) into the test story's testCriteria field — exact function signatures, error message strings, mock strategy — before the test story runs. Once present, testCriteria supersedes plain ACs as the ground truth the failure-analyst and spec-validator check against. Bypass: SKIP_TC_WRITER=1.

Step 2 — Create worktrees fixed (conditional)

Only runs if the phase has stories assigned to parallel lanes. Creates isolated git worktrees so parallel agents don't collide on the same working directory.

Steps 3a / 3b — Primary / Independent agent lanes fixed (conditional)

Run stories assigned to the "primary" and "independent" agent groups in their own worktrees, in parallel with each other and with the main-branch lane. Each lane's stories go through the same scope-guard/vendor-guard/verification/retry-ladder machinery described under Step 1.

Step 3.1 / 3.2 — Worktree health check & merge fixed (conditional)

Verifies each worktree lane is in a healthy state, then merges completed worktree branches back into the main branch. A failure in one lane doesn't block merging the other lane's completed work.

Step 3.5 — Post-parallel assessment fixed

Compares actual vs. forecast time/cost per story (against the Step 0.1 CPA estimate), and can correct agentRole assignments for future phases' pending stories if a systematic skill mismatch is detected (never modifies already-completed phases). Writes a human-readable improvement report to logs/phase-improvements/<phase>.md. recent Also runs with tool access now, for the same reason as Step 0.5.

Step 4.2 — Testing gates, Phase A fixed

Runs SAST and spec-validator in parallel. If either fails, Phase B and Phase C (below) are skipped entirely — see "Testing-gate phase sequencing" at the end of this step group.

4.2a — SAST sentinel

sast-sentinel receives pre-computed hard evidence injected into its prompt — real tsc --noEmit output, real npm audit results — and is explicitly told not to call tools; it classifies the pre-computed evidence rather than gathering its own. Classifies dependency CVEs: runtime deps can be blocker/major, dev-only deps (vitest, esbuild, vite, typescript, eslint, etc.) are always minor regardless of CVSS score.

recent Before SAST even runs, a deterministic self-heal step checks the tsc output for error TS18003 ("No inputs were found"). This recurred live when a phase's spec-pass split left no story creating an actual source file, so tsconfig.json's own include glob matched zero files. The fix reads the glob already on disk, and — if truly zero files match — writes one minimal placeholder file (export {};) at the location the glob implies (no hardcoded file names), re-runs tsc to confirm, and commits the placeholder to git so downstream phases see a clean state. Falls through to normal gate evaluation if tsc still fails for unrelated reasons.

4.2b — Spec validator

spec-validator classifies each story's acceptance criteria as met / partial / unmet / untestable. Receives real vitest results and the story ACs pulled straight from prd.json as pre-injected hard evidence, but must use its own Read-tool access to verify file-content-level criteria (e.g. exact package.json field values) — this is the one thing that isn't pre-injected.

recent Grounding check on the story-fail count: a story's fail verdict only counts toward blocking the gate if at least one of its criteria has a status other than untestable. If literally every criterion in every failing story is untestable (the agent had no real evidence — e.g. it never actually used its Read tool despite having access, observed live), the fail is downgraded to a non-blocking warning instead of aborting the phase. Implemented via story-boundary text slicing (line-level regex, not full JSON parsing — spec-validator output frequently contains raw newlines inside string values that break json.loads).

Testing-gate phase sequencing & gate-remediation (applies across 4.2 / 4.3 / 4.4)
  • Phase A (4.2) failing skips Phase B (4.3) and Phase C (4.4) entirely — they emit skip, not pending.
  • Each gate's exit-code check (sast_exit, spec_exit, etc.) only reflects whether the underlying agent process crashed — not whether the gate's content reported a real failure. recent Every gate's "agent ran fine, content says fail" branch now explicitly appends its own log to the remediation candidate list; previously only perf-sentinel had this fix, so the other five gates' content-based failures never reached self-heal remediation at all and went straight to a hard pipeline abort.
  • On a gate failure, a 3-agent remediation pipeline attempts to fix forward rather than aborting outright — see §3/§4 for each agent's role: gate-finding-analyst extracts a grounded finding, story-ac-remediator augments the owning story's ACs, profile-augmentor appends a preventive profile rule if the anti-pattern is novel.
  • When a gate's finding can't be grounded to a story by the LLM, recent a deterministic git-blame fallback now runs before giving up: it reads the finding's file path, runs git log --follow -1 on it, and extracts the owning story ID from the commit subject using the existing "story: complete <id> (N file(s))" convention every post-story commit already uses. Falls through to skipping remediation only if git has no matching commit.
  • A successful remediation signals the caller to reset and retry the phase (exit code 2) rather than hard-aborting.

3. Agent Roster & Responsibilities

profiles.json currently defines 50 agent profiles. Each is a flat {role: "prompt string"} entry — a named responsibility paired with the instructions that role follows. They fall into the categories below. Roles marked fixed exist in every project; unmarked implementation roles are generated per-project (see §1 and §4).

Initialization agents (run once, at project birth)
  • project-initiator-agent fixed — runs as INIT-001, the absolute first story in every project, before dashboards or any implementation work begins.
  • prd-project-manager-agent fixed — INIT-002, runs after project-initiator-agent completes. The authority on prd.json — validates its structure.
  • dashboard-orchestrator-agent fixed — DASH-001, the first task of every scaffolded project; static infrastructure agent responsible for the dashboard build.
  • dashboard-test-agent fixed — DASH-002, runs immediately after DASH-001. Read-only validation agent — never modifies dashboard files, only checks them.
  • dashboard-update-agent fixed — DASH-003, runs after DASH-001 and DASH-002 both pass. Validates real-time dashboard behavior.
  • agent-skills-agent fixed — SKILLS-001, a post-spec gate that runs after openspec-agent and speckit-agent have fully elaborated all stories, checking for skill gaps across the whole PRD.
Specification agents (Step 0)
  • readiness-checker fixed — pre-spec sub-stage; validates stories against INVEST criteria and a configurable checklist.
  • grooming-coordinator fixed — pre-spec sub-stage; orchestrates the backlog-grooming pipeline that runs before openspec/speckit.
  • dedup-detector fixed — pre-spec sub-stage; identifies semantically overlapping, duplicate, or conflicting stories.
  • spec-coordinator-agent fixed — reads the PRD before every phase, evaluates risk/dependencies/readiness, decides which spec personas run.
  • openspec-agent fixed — elaboration pass; see Step 0 above for full detail.
  • speckit-agent fixed — verification pass; see Step 0 above for full detail.
  • spike-agent fixed — runs exclusively on stories with storyType: spike; time-boxed technical discovery, never writes implementation code.
Coordination & assessment agents (run across the phase lifecycle)
  • team-lead-agent fixed — tri-modal: PRE-PHASE (Step 0.5 skill assessment), POST-PHASE (Step 3.5 forecast-vs-actual comparison), and TEAM-LEAD (general coordination).
  • test-coordinator-agent fixed — governs the testing-gate sequence between code review and unit-test verification; sequences the specialist testing agents in phases (see Step 4.2/4.3/4.4).
  • prd-model-coordinator fixed — Step 0.9; fills in missing model/provider/effort assignments.
  • tc-writer-agent fixed — Step 1.6; extracts verified test criteria from completed implementation source.
Testing-gate agents (Step 4.2 / 4.3 / 4.4 / 4.6)
  • sast-sentinel fixed — security/compilation issues; see Step 4.2a.
  • spec-validator fixed — acceptance-criteria compliance; see Step 4.2b.
  • review-agent fixed — general structural code review (findings by severity: blocker/major/minor) — the broader-scope counterpart to review-ranger's diff-level depth.
  • review-ranger fixed — deep, PR-level diff analysis; see Step 4.3a.
  • mutant-hunter fixed — mutation-testing quality assessment; see Step 4.3b.
  • fuzz-weaver fixed — fuzz/property-based edge-case analysis; see Step 4.4a.
  • perf-sentinel fixed — performance regression/bottleneck analysis; see Step 4.4b.
  • playwright-agent fixed — high-complexity browser E2E; see Step 4.6.
  • lightpanda-agent fixed — fast, deterministic browser E2E; see Step 4.6.
Self-heal & remediation agents (fire on failure, not on the happy path)
  • failure-analyst fixed — diagnoses story implementation failures; routes fixes to prd/tc/skill/kb/tool targets. See Step 1 and §4.
  • prd-change-reviewer fixed — validates every automated write to prd.json or profiles.json before it's accepted; snapshots before/after, reverts on fail.
  • kb-change-reviewer fixed — stricter variant of the above, specifically for permanent KB-{agentRole}.md writes (these persist across every future run, so the bar is higher).
  • gate-finding-analyst fixed — extracts a grounded finding from a failed testing gate's log and maps it to the owning story (with the git-blame fallback described under Step 4.2 sequencing).
  • story-ac-remediator fixed — augments the owning story's acceptance criteria with a concrete fix requirement, given the gate-finding-analyst's structured finding.
  • profile-augmentor fixed — checks whether a gate finding's underlying anti-pattern is novel; if so, appends a preventive rule to the relevant agent's profile.
Implementation agents (project-specific — generated per stack, not fixed)

Generated by epam new generate's proposeAgents() at project scaffolding time (see §1/§4), tailored to the project's declared tech stack. Common examples seen in TypeScript/Node projects:

  • typescript-engineer — writes implementation code.
  • test-engineer — writes test files only, never implementation.
  • frontend-engineer / ui-engineer — UI-focused implementation roles for projects with a frontend surface.
  • generator fixed — a narrow-purpose file generator: creates a single complete new file from a fully-specified prompt, with no need to read any existing file.

The engine imposes no fixed list of implementation roles — whatever roles a project's stack needs are created (or filled in mid-project by Step 0.5) as required.

Documentation agents (defined in profiles.json — see note on wiring)

doc-coordinator, doc-reviewer, guide-author, changelog-agent, docstring-agent, api-doc-generator, architecture-doc-agent, doc-index-builder, doc-search-agent, doc-site-builder — a full documentation-generation roster exists as fixed profiles. As of this writing these profiles are not yet invoked by any phase-loop code (no "documentation phase" currently calls them) — they exist as a ready-to-wire capability, not an active step in the pipeline described in §2.

4. Tools, Skills & Dynamic Generation

Three distinct things are all sometimes loosely called "tools" in this system — worth keeping separate: the built-in tools an agent uses during its own turn, the skills tracked per agent role, and dynamic tools the pipeline synthesizes for itself.

Built-in tools (what an agent can DO during its turn)

Read, Write, List, Search, Fetch, and Bash — the standard tool surface every implementation and gate agent draws on when it has tool access. Whether a given pipeline call grants this access is a wiring decision (AI_GATE_ALLOW_TOOLS=1 / run_orch_prompt_with_tools) made per call site, not a property of the agent role itself — several gate agents (SAST, the failure analyst, the PRD-change reviewer) deliberately do NOT get tool access because all the evidence they need is injected as text in the prompt; giving them tools they don't need adds nothing but cost and risk of an ungrounded tangent.

Skills (what an agent role is expected to know)

A story can declare technicalNotes.requiredSkills — plain-language skill tags (e.g. "TypeScript", "vitest", "Express routing"). Step 0.5's pre-phase assessment compares each story's required skills against its assigned role's existing profile text and appends missing-skill sentences proactively, before the story is ever attempted.

Reactively, when the failure analyst diagnoses a failure with target: skill, it proposes a short imperative "self-heal" sentence to append to the role's profile (e.g. "Always end TypeScript statements with semicolons..."). recent A deterministic pre-check (_skill_note_format_ok) verifies the objectively-checkable format rules — length ≤200 chars, imperative opener, no story-ID reference, not a duplicate of an existing line — before this goes to the LLM reviewer at all; if it already passes, the reviewer call is skipped entirely. Found live: the reviewer was rejecting already-well-formed notes 3/3 times purely on flaky format judgment, burning a gate round-trip each time for zero benefit — these are checkable facts, not something that needs an LLM's opinion.

Dynamic tool synthesis (the pipeline writing its own helper scripts)

When the failure analyst diagnoses a failure as a repeated MECHANICAL step — not a knowledge gap, but a multi-step shell recipe that's error-prone to repeat by hand (its own profile's example: "add a package to package.json and install it before importing it") — it can propose target: tool instead of a KB entry or skill note. This is reserved for cases where a KB rule alone has already failed to prevent the same class of failure.

The proposed script (a tool_spec: name, purpose, and the exact recipe) goes through the same run_change_with_reviewer_retry gate as any other self-heal write, using the tool_creation change type specifically — the reviewer checks the recipe is idempotent (safe to run twice), does nothing beyond its stated purpose, never deletes files or force-pushes git, and stays inside the project's own working directory. On approval, it's written to .epam/dynamic-tools/<name>.sh.

From then on, every subsequent agent prompt for that project automatically surfaces a list of available dynamic tools ("Use them via the bash tool instead of repeating the equivalent steps by hand") — the pipeline is literally extending its own toolset over the life of a project, scoped to that project's own .epam/dynamic-tools/ directory, not the shared engine.

Dynamic agent/profile generation (the pipeline writing its own agent roster)

Two distinct moments create new agent profiles, not just new tools:

  • At project birth — epam new generate's proposeAgents() (§1) generates the initial set of project-specific implementation roles from the manifest and clarification Q&A. This is a one-time, human-in-the-loop step (interactive confirmation unless --no-interactive is passed).
  • Mid-project — Step 0.5's pre-phase skill assessment can create a brand-new profile key from scratch if a phase's stories need a role that doesn't exist yet, based on the project's declared tech stack. No human confirmation step here — it goes through the same prd-change-reviewer gate (change type profile_creation) as any other automated profiles.json write, which checks the new profile states its file-writing scope, doesn't introduce out-of-stack technology, and doesn't duplicate an existing role's responsibilities.

5. Model Assignment & Cost Tracking

How a story's model gets assigned
  1. Explicit assignment already present on the story in prd.json — never overwritten.
  2. Step 0.9's PRD model coordinator fills any gap (model/aiProvider/reasoningEffort) based on effort/role.
  3. On a failed retry, assess_model_escalation may replace the model for that retry only, per the tier-aware ladder rules below.
The two escalation ladders

Config-driven (EPAM_MODEL_LADDER_MEDIUM / EPAM_MODEL_LADDER_HIGH), each a set of direct current→next model mappings rather than a fixed linear chain:

  • Medium: base models each jump directly to the medium ceiling model (single hop).
  • High: same single-hop pattern to the high ceiling model, plus a bridge mapping (medium-ceiling model → high-ceiling model) for a story already sitting at the medium ceiling that's classified high-tier and needs one more escalation.

EPAM_MODEL_LADDER (no suffix) explicitly overrides both tiers to the same table. EPAM_FINAL_FALLBACK_MODEL/_PROVIDER guarantee Rung 3 always has an escalated model even if the tier's ladder lookup produced nothing.

Cost recording

Every agent invocation (story implementation, gate agents, coordination agents) emits a cost record to phase-cost.jsonl: model, tokens in/out, computed cost (from model-pricing.json, falling back to prefix-matching if an exact model key isn't found), elapsed time, and status. Gate/coordination calls are tagged with an agent_type (e.g. assessment, qa-gate:sast) distinct from story-implementation records, so gate cost and story-implementation cost can be broken out separately. The CPA pre-pass (§2, Step 0.1) is the forecasting counterpart to this actuals ledger — its blended estimates are meant to be compared against what actually lands here.

6. Config-Driven Extensibility

The engine (claude.sh / run-agent-orchestration.sh) contains no hardcoded story IDs, file names, or stack/language assumptions. Everything project-specific is one of:

  • prd.json — what to build
  • profiles.json — who builds it, and the fixed gate/coordination roles' instructions
  • .epam/dependency-check.json — how to detect/install a missing dependency for this stack
  • .epam/contract-generation.json — how to auto-generate a dependency contract for this stack
  • Launcher-script env vars (e.g. EPAM_TEMPERATURE_MODEL_PATTERN, ORCH_GATE_MODEL, EPAM_MODEL_LADDER_MEDIUM/_HIGH) — project-level tuning, not engine code
