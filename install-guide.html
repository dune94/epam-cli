1. Prerequisites — what the installer actually checks

Nothing here is aspirational. Each row names the check that enforces it, so an operator can go and read the line rather than take this page's word for it.

Hard requirements — install.sh marks these ✗ and exits 1

RequirementThe installer's own reasonWhere it is checked
git"the pipeline works on git codelines"install.sh → need git
jq"the pipeline parses JSON with it throughout"install.sh → need jq
node"the engine and the CLI are node"install.sh → need node
python388 handlers under orchestrations/scripts/lib/handlers are executed with it. Every import is stdlib plus one local module — no venv, no pip install, no requirements.txt: the interpreter is the whole requirementinstall.sh, the python3 block
The active stack's runner CLI on PATH"the commonest real failure" — the run shells out to itinstall.sh, resolved from provider-sets.json → the stack's settingsFile → its first runners key

The runner is never named in a script — it is read from config. As declared today:

Neither claude nor codemie-claude is installed by this repo — codemie-claude is an internal EPAM tool obtained through your organization's own distribution. Rather than trusting the table above, have the machine answer for itself: ./orchestrations-installer/install.sh --check.

Node version

install.sh only checks that node EXISTS — it never checks the version. The requirement is real and enforced elsewhere: package.json declares "engines": { "node": ">=20.0.0" }, .nvmrc says 20, and pipeline-health.sh warns below major 18 ("20 is what's tested"). On the development machine the system node is v14.17.0 and is far too old.

An install with an old node on PATH passes need node and then fails at npm run build, because tsup needs 20. Put 20 on PATH first, or pass it explicitly — install.sh, pipeline-services.sh and pipeline-health.sh all honour NODE_BIN:

export PATH="$HOME/.nvm/versions/node/v20.20.0/bin:$PATH"
# or
NODE_BIN=~/.nvm/versions/node/v20.20.0/bin/node ./orchestrations-installer/install.sh

Optional — a container runtime

Docker is optional, always, and never a reason for the install to fail: "an installer that fails because a container is missing teaches people to skip the installer". With no runtime running, the default auto mode warns and carries on — the dashboards, Langfuse and Grafana are observability, and the pipeline runs without them. See §3.

Platform and headroom — from pipeline-health.sh

  • Linux, WSL2 or macOS. Anything else is warned about as untested.
  • bash >= 4 — "this pipeline's own scripts assume bash >=4 in places".
  • ≥ 2 GB free memory, or it is a hard FAIL: "a run is likely to OOM this machine". Under 4 GB is a warning — "fine for a single run, tight for a run plus dashboards".
  • ≥ 5 GB free disk at the install root, or it warns.

What the installer cannot supply for you

  • Client codelines cloned on disk. A brownfield project's JIRA_CODELINE_ROOT must exist and contain git repos — the pipeline scans that directory, nothing lists repos by name.
  • Jira credentials — see §5. This is the one that catches people.

2. Install — npx amsd-pipeline, and every flag

No git commands required. This clones the repo itself, packages the requested ref into a fresh tree at --dest, then runs every step below against that tree.

SEED YOUR .env FILES INTO --dest FIRST — before you run the installer, not after. This is the difference between an install that works in one run and one that silently does not.

install.sh starts two long-lived host daemons as part of the install, and runner-host reads its credentials once, at startup, from the .env files as they stand at that moment. Install first and fill the files in afterwards and the daemon keeps the blank values it started with: Langfuse traces silently never appear, and the installer reports ✓ ready the whole time, because nothing is wrong with the install — only with what the daemon is holding.

So do this, in this order:

DEST=~/amsd-pipeline

# 1. Create the tree and seed the credentials BEFORE installing.
mkdir -p "$DEST/launch-dashboard" "$DEST/orchestrations/jira"
cp /path/to/your/.env                    "$DEST/.env"
cp /path/to/your/launch-dashboard.env    "$DEST/launch-dashboard/.env"
cp /path/to/your/<project>.env           "$DEST/orchestrations/jira/<project>.env"

# 2. Now install. It packages around the files you placed and never overwrites them.
npx amsd-pipeline --dest "$DEST"

install.sh only creates a .env from its template when one is absent, so seeding first is safe: your file is used as-is, and you will not see the ! .env created from .env.example — FILL IT IN warning, which is itself the signal that you installed before seeding.

If you have already installed and are fixing it up afterwards, that is recoverable — edit the .env files and re-run install.sh against the same --dest. It compares the daemon's startup environment against the files as they stand now and restarts it when they differ (saying so: restarting runner-host … its .env has changed since it started). Nothing else restarts daemons: not by hand, not with pipeline-services.sh — the installer owns them.

The plain form, once your files are in place:

npx amsd-pipeline --dest ~/amsd-pipeline

From an existing checkout, the same script works directly, in place:

./orchestrations-installer/install.sh                    # install for the default stack, with dashboards if docker is up
./orchestrations-installer/install.sh --stack codemie     # install for a specific stack
./orchestrations-installer/install.sh --no-docker         # skip dashboards entirely
./orchestrations-installer/install.sh --check             # verify an existing install, change nothing
./orchestrations-installer/install.sh --dest ~/somewhere --ref v1.7   # package that ref into a NEW tree, then install it

npx amsd-pipeline is the very same script — bin/amsd-pipeline.js does nothing but spawnSync('bash', [install.sh, ...argv]), so every flag below works identically through either entry point. Read straight out of install.sh's own argument parser, this is the complete list:

FlagEffect
--dest <path>Package the ref into <path> and install that tree; creates it if absent. Without it, install.sh only ever configures the tree it is already sitting inside.
--ref <tag|sha|branch>Which commit to package. Default HEAD. Tags are fetched first, so a ref a colleague just pushed still resolves.
--repo <url>Clone source when install.sh was obtained alone (npx, a raw download). Default https://github.com/dune94/amsd-pipeline.git; also settable as EPAM_REPO.
--stack <name>Which provider set to install for. Default: provider-sets.json's defaultSet, or EPAM_PROVIDER_SET. An unknown name errors and lists the declared stacks — never a silent fall-through onto another stack.
--no-dockerSkip the observability stack and the launch dashboard entirely.
--dockerREQUIRE a container runtime — fails if none is running. The default auto merely warns.
--replay on|offDefault off. on makes Langfuse record every run so it can be replayed later for $0. Also settable as EPAM_REPLAY. An invalid value is rejected outright — never silently downgraded to off, because "a run not recorded can never be replayed" is a one-way loss.
--checkVerify an existing install, change nothing.
--uninstallRemove only this install's docker footprint and host daemons — never files. Accepts --dest. See §10.
--help, -hPrints the script's own header.

Environment variables the installer reads: EPAM_PROVIDER_SET, EPAM_REPLAY, EPAM_CONTAINER_RUNTIME, EPAM_REPO, EPAM_PROJECT, EPAM_BIN_DIR (default ~/.local/bin, where the epam shim is written), EPAM_COMPOSE_FILE, EPAM_MIN_DIST_BYTES, EPAM_LAUNCH_HEALTH_TRIES, EPAM_LAUNCH_HEALTH_INTERVAL, NODE_BIN, and — together with EPAM_PROJECT — JIRA_URL, JIRA_PROJECT_KEY and JIRA_CODELINE_ROOT, which it writes into that project's config.env for you (non-secret values only; it never writes a token into project config).

If you did not seed .env first, the first install is a TWO-STEP operation

Seeding beforehand (above) is the one-run path. Starting from nothing instead, the installer copies its template and says so — ! .env created from .env.example — FILL IT IN before running — and then checks the values, not just the file: if the selected stack declares a required credential that is still empty, the install FAILS with ✗ the '<stack>' stack needs these, still empty in .env: OPENROUTER_API_KEY .... So:

./orchestrations-installer/install.sh --dest ~/amsd-pipeline --ref v1.51   # creates .env, then fails
$EDITOR ~/amsd-pipeline/.env                                              # fill it in
./orchestrations-installer/install.sh --dest ~/amsd-pipeline --ref v1.51  # re-run — now it completes

On the default claude stack, which declares no required credentials, an install can complete with an empty .env — the file is still created, and still needs the Jira values before a brownfield run will start.

--replay on FAILS the install unless both Langfuse keys are set. Not a warning, deliberately: LangfuseTracer gates on both LANGFUSE_SECRET_KEY and LANGFUSE_PUBLIC_KEY, so with either missing the containers run and capture nothing while the operator believes recording is on — and a run that was never recorded can never be replayed.

The installer reads them from the install's own .env as well as the surrounding shell, and reports ✗ replay: on but missing: … rather than proceeding. With --replay off (the default) it states the consequence either way: "runs will NOT be replayable".

Re-running install.sh against an existing --dest is an UPDATE, not a fresh install: app code updates, but an operator's edited project config (config.env, llm-settings.json, five engine-wide orchestrations/config/*.json files) and accumulated run state (orchestrations/logs, phase-cost.jsonl, KB files) both survive untouched.

Prerequisites are listed in full in §1 — git, jq, node (version unchecked by the installer, but 20 is required), python3, and the declared stack's own runner.

3. Docker or Podman — no Docker Desktop license needed

install.sh discovers whichever is on PATH — Docker first, Podman as a fallback (EPAM_CONTAINER_RUNTIME to force one). Docker Desktop requires a paid subscription above 250 employees or $10M revenue — that is a procurement conversation, not a technical requirement, and this installer never needs it: install Docker Engine directly inside a WSL2 Ubuntu distro (the standard apt-based Docker CE install), or use Podman, either is fully supported and tested (test/unit/orchestration/the-installer-installs-on-podman.test.ts). Neither docker nor podman is required at all — pass --no-docker and the pipeline itself still runs; only dashboards and the launch UI are unavailable.

Every docker resource — container names, network subnet, ports — is isolated per install, deterministically, so two installs (or an install alongside a hand-run dev checkout) never collide on the same machine.

4. The .env files — and every variable in them

Order matters: place these into --dest before running the installer — see §2. The runner-host daemon reads them once at startup, so filling them in afterwards leaves it holding blank credentials while the install still reports ✓ ready. Recoverable by re-running install.sh, but seeding first makes it one run.

Several separate files, each scoped to a different concern — documented here in full because an earlier version of this install flow omitted some of them entirely and it caused real confusion mid-run:

FileHolds
Root .envProvider credentials (OPENROUTER_API_KEY, MINIMAX_API_KEY — only for the openrouter stack) plus feature-scoped vars (JIRA_EMAIL/JIRA_TOKEN, LANGFUSE_SECRET_KEY/LANGFUSE_PUBLIC_KEY, GITHUB_PERSONAL_ACCESS_TOKEN). Generated by install.sh from provider-sets.json + env-vars.json — a var added to either needs no installer edit. The claude stack needs none of these: it authenticates via claude login (an OAuth session on disk), and an ANTHROPIC_API_KEY present here outranks that session and silently bills the API account instead — leave it unset for the claude stack.
launch-dashboard/.envLAUNCH_PASSWORD (a fixed default, abcd1234, the same on every fresh install — change it via the dashboard's own change-password flow after your first login) and LAUNCH_UI_PORT.
A project's own config.envOperational settings, not secrets — JIRA_URL, JIRA_PROJECT_KEY, JIRA_CODELINE_ROOT (the brownfield discovery root — a real host path to the client repos), etc. Preserved across installer updates.
A project's own orchestrations/jira/<project>.envPer-project Jira credentials, when a project's config.env declares SECRETS_FILE= pointing at it — an opt-in override of the root .env defaults, for running against multiple clients' Jira instances without sharing credentials. Not provisioned by install.sh at all, and not carried into a new install either — see §5.

A project’s own secrets file — <install>/orchestrations/jira/<project>.env

Used only when that project’s config.env sets SECRETS_FILE to point at it. It holds JIRA_EMAIL and JIRA_TOKEN (obtained exactly as above) plus CODEGRAPH_ENABLED (1 or 0 — whether the code-graph index is built for this project). Values here override the root .env, which is how one install serves several clients without sharing credentials. The installer never creates or copies this file — see §5.

A complete example, for a project whose config.env sets SECRETS_FILE=orchestrations/jira/metrolinx.env:

# <install>/orchestrations/jira/metrolinx.env
JIRA_EMAIL=jane.doe@yourcompany.com
JIRA_TOKEN=ATATT3xFfGF0…  (starts ATATT, ~190 characters)
CODEGRAPH_ENABLED=1

Confirming the values are right

./orchestrations-installer/install.sh --dest <install>   # validates, and restarts services whose .env changed
<install>/orchestrations/scripts/pipeline-health.sh      # reports what is ready

The installer names every required variable that is still empty and stops. It does not test whether a token is valid: a present-but-wrong token passes the install and fails at the first Jira call, reporting Jira’s own error.

5. Jira credentials are NOT carried into a new install

A fresh --dest install has no Jira token, and nothing tells you so until the run dies. The install reports ready; the launcher then stops with JIRA_TOKEN is not set. Export it or add it to .env before launching.

A project's tokens live in the file its own config.env declares as SECRETS_FILE. For the metrolinx project that is:

<install>/orchestrations/jira/metrolinx.env

It holds JIRA_EMAIL and JIRA_TOKEN (plus CODEGRAPH_ENABLED) — not the root .env, and not orchestrations/projects/metrolinx/config.env, which deliberately carries only JIRA_URL, JIRA_PROJECT_KEY and this tracker's field schema.

Three independent reasons a new install cannot have inherited it — each checked, not assumed:

  • .gitignore:104 ignores orchestrations/jira/*.env (only *.env.example is committed), so the file is untracked — git ls-files orchestrations/jira/ returns only .env.example, docker-compose.yml and setup.sh.
  • --dest populates the new tree with git archive, which can only ship tracked files.
  • It appears in neither operator-config-paths.json nor generated-run-state-paths.json, so no snapshot/restore step touches it either.

Copy it forward yourself — ideally before installing, along with the other .env files (§2):

cp ~/previous-install/orchestrations/jira/metrolinx.env \
   ~/amsd-pipeline/orchestrations/jira/metrolinx.env
chmod 600 ~/amsd-pipeline/orchestrations/jira/metrolinx.env

Skip it and the run stops at the launcher, because metrolinx's config.env declares REQUIRED_KEYS=JIRA_TOKEN.

8. The launch dashboard & runner

install.sh provisions the launch dashboard (Flutter frontend + Node backend) fully by itself: builds and isolates its docker stack, creates launch-dashboard/.env with the default password, and starts runner-host.js — the HOST process (not dockerized; a container cannot exec a host process) that actually polls the spool and launches real pipeline runs — as a managed, pidfile-tracked daemon. A second daemon, snapshot-watch.js, is also started automatically: it keeps agent-monitor's build-info.json fresh, and without it every launched run's own pre-flight hard-fails immediately.

9. Bouncing services — pipeline-services.sh

For a WSL restart, or just wanting to restart cleanly, without losing any data (never -v, never --rmi — this is a pause, not an uninstall):

bash orchestrations-installer/pipeline-services.sh --stop
bash orchestrations-installer/pipeline-services.sh --start

--start reconnects to the exact subnet/ports/project identity the original install resolved (persisted in .pipeline-services-state.env), never re-rolling a different one.

10. Checking readiness — pipeline-health.sh

A different question from install.sh --check ("did the install complete") — this asks "can I launch a real run from here, right now":

bash orchestrations-installer/pipeline-health.sh                       # the tree this script lives in
bash orchestrations-installer/pipeline-health.sh --dest ~/amsd-pipeline  # a specific install

Pass --dest whenever you are not standing inside the install you mean: without it the script resolves the tree from its own location, which is wrong the moment anything else runs it. install.sh runs this itself as its last step — advisory, but if it reports problems the installer's final word is "installed, but NOT ready to launch" and it exits 1.

Checks platform/tooling, probes the container runtime rather than trusting command -v, reads the active provider set live and flags the API-key-outranks-OAuth trap explicitly, checks memory/disk headroom, verifies a selected project's codeline-discovery root actually resolves to git repos, and confirms both host daemons (runner-host.js, snapshot-watch.js) are actually running — reporting unhealthy, not just a warning, if either is declared but not running.

11. Uninstalling

bash orchestrations-installer/install.sh --uninstall --dest ~/amsd-pipeline

Removes this install's docker footprint — containers, network, volumes, locally-built images — and stops both host daemons. Structurally incapable of touching another install or the dev checkout: an isolated install's project names never share the dev checkout's own naming shape, by construction. Files on disk are never touched; remove the directory yourself once you are done with it.

12. Troubleshooting

SymptomWhat it means
Install reports "ready" but the dashboard login failsThe running container may have started before a .env edit — the file and the live process can desync. Restart with pipeline-services.sh --stop then --start to pick up the current file.
A launched run fails pre-flight instantlyRun pipeline-health.sh first — it checks exactly the things a run's own pre-flight also checks (both host daemons, credentials, memory), before you spend anything.
"MINIMAX_API_KEY is not set" on the claude stackYou are on one of the older per-project launchers, which check every vendor's key unconditionally regardless of the active stack — tier3-metrolinx-run.sh:153 and tier3-skyscanner-app-run.sh:89. Neither install.sh nor the supported entry point has this problem: orchestrations/scripts/pipeline → orchestrate.sh reads the ACTIVE set's declared credentials (lib/set-credentials.sh), and the claude stack declares none. Use §6.
JIRA_TOKEN is not set right after a successful installA fresh --dest install cannot have inherited the project's secrets file — it is gitignored, so git archive could not carry it. Copy it from your previous install: §5.
The install fails at npm run build with the prerequisites all ✓Almost certainly the node version. install.sh checks that node exists, never which version it is; tsup needs 20. §1.
A saved run stays "pending" forever after it actually failedThe dashboard's database and the pipeline's own status file can desync — check launch-dashboard/spool/status/<id>.json for the real outcome.
