What this system does

This engine turns a written specification — what needs to be built, and how to know it's done correctly — into working, tested code. It does this by coordinating a series of AI agents, each with a specific job, working through the specification one piece at a time. A human defines what needs to be built and what "done" looks like; the engine coordinates the agents that build it, check it, and confirm it meets the stated criteria before moving on.

Work is organized into phases (e.g. "scaffold," "core," "ui_and_review"), and each phase is made up of stories — individually scoped units of work with their own acceptance criteria. The engine works through one phase at a time, and within a phase, through its stories, in a defined order.

The three required inputs

Every orchestration run is driven by three files. All three exist before any agent writes a line of code.

Required

prd.json

The master specification. Contains the full list of stories to be built, each with:

  • A unique ID and title
  • A plain-language description of what to build
  • Acceptance criteria — the specific, checkable conditions that define "done"
  • Which files it's expected to create or modify
  • Which phase it belongs to, and what it depends on
  • Which agent role is responsible for it

It also defines the phase order (implementationOrder) — which stories run in which phase, and in what sequence.

Required

profiles.json

Defines the agent roles available to the engine. Each entry is a named role paired with the instructions that role follows — its area of responsibility, the conventions it must respect, and (for implementation roles) the technology stack it works in.

Profiles fall into two groups:

  • Fixed roles — provided by the engine itself, not something a project author writes (for example, the quality-check agents described below). These already exist, unchanged, in every project.
  • Project-specific roles — generated for each project based on its tech stack (for example, a TypeScript engineer role, or a test-writing role). These are tailored to what the project actually needs.
Setup-only

manifest.md

A human-authored input, not something the pipeline generates. Think of it the way you'd think of a package.json or Python's requirements.txt — a short declarative brief that says what this project is and what it needs, written once by a person before any tooling runs against it. No project ships with one already in place; someone has to write it, the same way no project ships with its dependencies already declared for you.

The manifest is not read directly by the orchestration engine while it runs. Its only job is to be the source material the engine reads once, up front, to generate the first draft of prd.json and the project-specific entries in profiles.json for a brand-new project.

How a new project gets set up

Setting up a new project is a two-step, one-time process, run before any orchestration begins. Two things must exist before generation can run: a scaffolded directory (step 1) and a manifest a human has actually written (step 2) — there is no default or template manifest shipped with the project, the same way there's no default package.json shipped with a new Node project.

1

Scaffold structure

Creates the project's directory structure — scripts, dashboards, settings. No AI involved at this step.

2

Write the manifest

A human writes manifest.md: project name, tech stack, requirements, constraints. Nothing generates this for you.

3

Generate PRD + profiles

An LLM reads the manifest, may ask clarifying questions, and produces prd.json (the story list) and the project-specific entries in profiles.json.

4

Ready to run

With prd.json and profiles.json in place, the project is ready for the orchestration engine to begin working through its phases.

The orchestration flow (running a phase)

Once a project has its prd.json and profiles.json, the engine works through the phases defined in the PRD one at a time. For each phase, the same sequence runs:

1

Specification pass

The stories assigned to this phase are reviewed and elaborated — acceptance criteria are refined, and a story may be split into smaller pieces if it covers too much ground for one unit of work.

2

Story implementation

Stories are handed to the appropriate agent role in order. Each agent writes the code needed to satisfy its story's acceptance criteria.

3

Testing gates

A set of automated quality-check agents review the phase's output — correctness, security, test coverage, and performance are each checked independently.

4

Phase complete

Once the phase's stories are implemented and its gates pass, the engine moves on to the next phase in the PRD's defined order.

Every story goes through an external verification step after the agent writes it — its own tests are run, and a type/compile check is performed, before the story is considered complete. If a story's own verification doesn't pass, the engine retries it before moving on.

The kinds of agents involved

Agents in this system fall into three broad categories:

Implementation agents

These are project-specific (defined per project in profiles.json, based on its tech stack). They write the actual code, and the tests for that code, against a story's acceptance criteria. A typical project has at least one engineering role (writes implementation code) and one testing role (writes test files only).

Testing-gate agents

These are fixed, built-in roles that run automatically after a phase's stories are implemented. Each one checks a different dimension of quality:

sast-sentinelSecurity and compilation issues
spec-validatorWhether each acceptance criterion is actually met
review-rangerCode review — quality and maintainability
mutant-hunterWhether tests actually catch real bugs
fuzz-weaverEdge cases and unexpected inputs
perf-sentinelPerformance issues in changed code

Coordination agents

These fixed roles support the process itself rather than writing product code — for example, the specification-pass agents that elaborate and split stories, and an assessment agent that checks whether the right agent roles are assigned to the right stories before a phase begins.
